# `Store.read()` 사용처 제거 계획

`Store.read()`는 현재 깊이 동결된 스냅샷을 복제 없이 반환한다. 따라서 호출명을 바꾸는 것만으로는 속도가 개선되지 않는다. 목표는 업무 코드에 전체 `DatabaseState`를 노출하지 않고, 필요한 자료와 버전만 저장 계층의 이름 있는 조회로 받는 것이다. 쓰기 직렬화와 확정된 스냅샷의 일관성은 유지한다.

운영 코드의 호출은 33곳이다. 버전만 확인하는 6곳, API의 기준 자료·가져오기 배치 조회 2곳, 신청·이력·초안·가져오기·확정·복원 서비스의 여러 자료를 결합하는 조회 24곳, 서버의 읽기 전용 핸들러 1곳으로 나뉜다. 테스트의 `store.read()`는 별도로 많으므로 운영 코드 이관 후 다룬다. 어댑터의 `read()`는 DB 재시작·복구에 필요한 별도 계약이다.

1. **버전 조회:** `Store.version()`에서 epoch와 revision만 반환한다. 가져오기 검토, 이력 반영, 백업·복원, 현황 다운로드의 버전 확인을 교체한다. 같은 응답 안에서는 두 값을 한 번에 읽고, 이전과 같은 충돌·재시도 결과를 테스트한다.
2. **단순 목록·단건 조회:** 학기·회원·강좌 목록과 가져오기 배치 단건 조회를 저장 계층의 명시적 조회로 옮긴다. 필요한 필드만 반환하고 정렬·페이지 결과와 없는 대상의 응답을 비교한다. 큰 원본 자료를 읽지 않는 경로부터 성능을 측정한다.
3. **복합 업무 조회:** 신청·이력·초안·확정·복원·가져오기 미리보기의 참조 자료를 업무별 읽기 모델로 묶는다. `Store.query(callback)`처럼 전체 상태를 다시 노출하는 이름 바꾸기는 하지 않는다. 한 업무의 여러 자료는 같은 확정 스냅샷에서 읽고, 쓰기·복원과 겹치는 요청의 revision 검사를 보존한다. SQL이 이득인 조회만 `backend/src/storage/queries/`의 전용 쿼리로 이동한다.
4. **공개 API 제거:** 서버의 읽기 전용 핸들러와 테스트를 새 조회 계약으로 옮긴 뒤 `Store.read()`를 삭제한다. `npm run verify`, `npm run test:browser`, `npm run test:storage-scale`, 복구·충돌 테스트를 통과시키고 운영 코드에서 `store.read()` 호출이 0곳인지 확인한다.

각 단계는 별도 커밋으로 검증한다. 1번을 완료해 버전 확인 6곳을 옮겼고, 2번의 기준 자료 목록·가져오기 배치 단건 조회 2곳도 전용 조회로 옮겼다. 운영 코드의 `Store.read()` 호출은 33곳에서 25곳으로 줄었다. 복합 업무 조회와 서버의 읽기 전용 핸들러는 3~4번 순서로 진행한다.
