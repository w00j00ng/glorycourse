# 저장소 전체 처리 점검과 현재 동작

2026-10-04 작업 브랜치의 구현 기준이다. 일반 자료 수정은 메모리에서 변경 부분만 복사하고 SQLite에서도 변경된 행만 저장한다. 전체 상태를 읽는 `Store.read()` 호출은 별도 [제거 계획](store-read-removal-plan.md)에 따라 줄인다. 전체 DB·테이블 처리 경로는 다음과 같다.

| 경로 | 판단과 조치 |
| --- | --- |
| 일반 등록·수정·삭제 | 변경 행만 검증·저장한다. 전체 테이블 삭제나 DB 파일 복사는 없다. |
| DB 최초 생성 | 비어 있는 스키마에 초기 자료를 삽입한다. 기존 테이블을 지우는 SQL은 없으며 `Store.open()`은 입력 분리와 전체 검증을 수행한다. |
| 내부 `Store.restore()` | 현재 상태와 후보의 차이만 한 트랜잭션에서 반영한다. 후보 분리·전체 검증·안전 사본 콜백은 유지한다. 이전 상태 없이 채워진 DB를 덮어쓰려는 호출은 거부한다. |
| 스키마 마이그레이션 | 버전별 SQL이 필요한 기존 행을 변환한다. 확정 초안을 별도 영수증으로 옮긴 뒤 해당 초안 행만 삭제하는 일회성 이관은 유지한다. |
| 마이그레이션 전 안전 사본 | `sqlite-snapshot.ts`의 `VACUUM INTO`로 완전한 SQLite 사본을 `update-backups`에 만든다. 원본·사본의 무결성, 파일 동기화와 SHA-256 확인을 유지한다. 일반 저장·Excel 반영·배정 확정은 자동 사본을 만들지 않는다. |
| 시작 시 DB 읽기·내부 복원 후보 분리 | 메모리 초기 적재와 호출자 자료로부터의 분리를 위해 전체 검증·복제를 유지한다. 일반 저장의 전체 복제와는 별개다. |
| 사용자 수동 백업·복원 | 화면·API·전용 서비스는 제거했다. 기존 파일·복원 영수증 테이블은 유지하며 자료 보관·재등록은 신청·이력 현황 Excel을 사용한다. |

학생 소속 migration `1791072000`은 신청·초안 항목·이력과 두 종류의 배정 스냅샷에 nullable 컬럼만 추가한다. 기존 행은 소속 null로 유지하며 스냅샷이나 전체 테이블을 재작성하지 않는다. 기존 null 소속의 fingerprint는 유지되고 회원 자료에서 소속을 관리하지 않는다. 상세 컬럼과 수정 범위는 [학생 소속 계약](contract-decisions.md#c-14-학생-소속의-시점별-보관)에 있다.

내부 검증 기준: 후보의 회원 한 명만 달라질 때 다른 행에 삭제 방지 트리거를 걸어도 성공하고, 재시작 후 자료가 일치해야 한다. 이전 상태가 없는 덮어쓰기 시도는 자료를 바꾸지 않아야 한다. 기존 `tests/integration/sqlite-incremental.test.mjs`·`store.test.mjs`·`recovery.test.mjs`·`migrations.test.mjs`로 변경 행 저장·실패 복구·안전 사본을 확인한다. 현재 시험 결과는 [문서 검증 및 개정 기록](documentation-review.md)에 기록한다.
