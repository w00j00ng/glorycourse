# 계약 결정 기록

현재 구현의 API·저장·업무 규칙을 정리한다. 사용자 화면 안내는 [사용 설명서](usage.md), 개발·검증 절차는 [개발 환경](development.md)에 있다. API의 필드·응답은 [OpenAPI](../openapi/openapi.yaml), 실제 DB 변경 이력은 [SQL migrations](../schema/migrations/)를 함께 확인한다.

## C-01 학기 문맥 revision

`Semester.allocationInputRevision`을 학기 문맥의 낙관적 잠금 값으로 사용한다. `PATCH /semesters/{id}/context`는 `expectedRevision`을 받고 학기명·순서·개설 강좌·정원을 같은 저장 명령에서 반영한다. 현재 구현은 문맥 저장 성공 시 대상 학기의 revision을 증가시킨다. 같은 값을 다시 저장해도 증가할 수 있다. 공통 강좌명을 변경하면 그 강좌가 개설된 다른 학기의 revision도 증가시킨다.

학기 관리 화면은 순서 번호를 직접 수정하지 않는다. `POST /semesters/{id}/move`는 화면에서 인접한 두 학기의 순서를 한 저장 명령에서 교환하고 두 학기의 revision을 증가시킨다. 요청 시 예상 순서와 인접 학기 ID를 확인해 오래된 화면의 이동 명령을 거부한다.

## C-02 세부 저장 구조

`schema/store-schema.json`이 서비스가 만드는 관계형 상태의 논리 계약이다. SQLite의 `store_meta`와 업무 테이블은 모든 값을 명시 컬럼에 저장하고, 반복·중첩 값은 부모 FK와 `position`을 가진 자식 테이블에 저장한다. 범용 전체 저장 DTO와 JSON `document` 컬럼은 사용하지 않는다. 한 업무 명령에서 변경된 행은 한 SQLite 트랜잭션으로 반영한다. DB 스키마는 `schema/migrations/`의 Unix timestamp SQL과 `schema_migrations`로 관리한다. 업데이트 안전 사본은 SQLite 파일이며, 미배포 개발용 `db.json`은 자동 이전하지 않는다.

일반 명령은 직전 자료와 다른 행 및 변경된 자식 자료만 저장한다. 수정되지 않은 가져오기 원본과 배정 스냅샷을 다시 기록하지 않는다. 트랜잭션을 시작한 뒤 DB의 epoch·revision이 직전 자료와 같은지 확인한다. 초기 생성은 빈 테이블에 삽입하고, 내부 `Store.restore()`도 현재 상태와 후보의 차이만 반영한다. 이전 상태 없이 채워진 DB를 덮어쓰는 전체 교체 경로는 없다. UNIQUE 값 교환에 사용하는 임시 값은 트랜잭션 안에서만 존재하고 커밋 시 FK·고유성 제약을 만족해야 한다.

`inputSnapshot`은 대상 학기, 개설 강좌, 신청, 희망, 관련 과거 이력, 동일 학기 기존 이력만 담는다. `sourceApplicationId`와 생성 당시 choice ID는 역사적 식별값이며 live FK가 아니다. 현재 final 회원·강좌와 업무 테이블 참조만 live 검증 대상이다.

수강이력은 수강신청과 배정초안의 생명주기에 종속되지 않는다. 확정으로 생성된 이력도 초안 식별자를 저장하지 않으며, 신청 또는 초안을 삭제해도 수강이력은 유지된다.

최종 변경 사유는 `note`, 이관 결정은 entity/action별 허용 필드, 확정 경고는 subject와 `changeCode` 컬럼으로 제한한다. 새 필수 값을 추가할 때는 SQL migration으로 해당 컬럼이나 자식 테이블을 추가한다. `ValidationIssue`는 화면 심각도와 실행 차단/확인 단계를 별도 배열로 유지한다.

## C-03 멱등 키와 requestHash

멱등 키의 조회 범위와 hash 입력은 작업별로 다르다. 공통 HTTP 요청 전체를 hash하는 방식은 아니다.

| 작업 | 기존 성공 결과 조회 | SHA-256 입력 |
| --- | --- | --- |
| Excel 반영 | 저장된 반영 결과의 `previewId`, `storeEpoch`, `Idempotency-Key` 일치 | 서비스 입력 전체를 객체 키 정렬 후 JSON 직렬화. 배열 순서는 유지 |
| 배정 확정 | 독립된 확정 영수증 중 같은 `Idempotency-Key` | 초안 ID, 준비 토큰, 예상 초안 revision, 확인한 경고 digest와 사유를 정해진 필드 순서로 직렬화 |

동일 범위·키·hash는 저장된 성공 receipt를 반환하고 새 쓰기를 하지 않는다. 같은 범위·키에 다른 hash는 HTTP `409 CONFLICT`다. receipt 검색은 준비 토큰·revision 만료 검사보다 먼저 수행한다. 배정 확정 영수증은 `finalization_receipts`와 자식 테이블에 독립적으로 저장되므로 확정 초안이 제거된 뒤에도 같은 확정 요청은 기존 결과를 반환한다.

수동 백업·복원 API는 제거했다. 이전 복원 영수증의 DB 테이블과 자료는 계속 유지한다.

## C-04 Preview와 준비 토큰

- 수강이력 단건·일괄 작업의 준비 토큰은 기본 5분, 초안 확정 준비 토큰은 기본 10분 후 만료된다.
- Excel Preview는 기본 15분 후 만료된다. 기준은 각각 `EnrollmentService`, `FinalizationService`, `ImportPreviewService` 생성자의 기본값이다.
- 미반영 Preview는 프로세스 메모리에 있어 재시작 시 만료된다. `STAGED` 배치의 rawRows는 SQLite에 보관하며 재검토로 새 Preview를 만든다. 반영 성공 시에도 `APPLIED` 배치에 rawRows·결정·receipt를 저장한다.
- 이력 작업은 입력·warningDigest·storeEpoch·storeRevision·만료를 서명한 토큰으로 검증한다. 초안 확정은 여기에 초안 revision과 선택 결과 digest를 함께 검증한다.
- 프로세스 재시작은 미커밋 토큰을 무효화한다. 이미 저장된 동일 성공 receipt 조회에는 새 쓰기용 토큰이 필요하지 않다.

## C-05 최초 안전 한도

`openapi/openapi.yaml`의 `x-operational-limits`에 최초 한도를 선언한다. 아래 업로드·workbook 한도는 `DEFAULT_WORKBOOK_LIMITS`, 자동 배정 한도는 배정 엔진의 검증과 대조한다.

| 항목 | 값 |
|---|---:|
| 업로드 파일 | 20 MiB |
| 압축 해제한 workbook | 100 MiB |
| workbook 시트 | 20 |
| workbook 행 합계 | 100,000 |
| workbook 셀 합계 | 1,000,000 |
| 한 학기 자동 배정 신청자 | 10,000 |
| 한 학기 개설 강좌 | 1,000 |
| 신청당 희망 강좌 | 5 |

구현된 한도의 초과 입력은 `413` 또는 계산 전 업무 제한 오류로 전체 거절하며 일부만 자르지 않는다. 이 값은 대상 PC에서의 처리 속도 보장이 아니다. 부하 시험과 익명화한 실제 자료 검증으로 측정한 뒤 조정한다.

`storeBytes: 209715200`(200 MiB)은 이전 전체 자료 후보 제한의 선언으로 남아 있다. 현재 일반 저장·DB 열기·내부 복원 경로에는 이 값을 읽어 크기를 거절하는 검사가 없다. 전체 자료나 SQLite 파일의 200 MiB 한도가 강제된다고 안내하지 않는다. 계약 테스트의 선언값 비교도 실행 경로의 제한 검증을 대신하지 않는다.

## C-06 목록과 오류 계약

목록 응답은 `items`, `page`, `limit`, `total`을 반환한다. `page` 기본 1, `limit` 기본 50·최대 200이다. 수강신청·수강이력은 `memberName` 부분 검색, `semesterId`와 `courseId` 정확 일치를 AND로 적용한다. export는 페이지가 아니라 같은 필터의 전체 결과를 대상으로 한다.

수강이력 목록과 일반 export는 `sort`로 `NAME_ASC`, `NAME_DESC`, `COURSE_ASC`, `COURSE_DESC`, `SEMESTER_ASC`, `SEMESTER_DESC`를 받는다. 생략하면 등록순이며 다른 값은 400이다. 필터 후 전체 결과를 정렬한 뒤 페이지를 나눈다. 학기는 숫자 순서로 비교하며 미정은 양방향 모두 마지막에 둔다. 동률은 최신 학기·회원명·강좌명·ID 순으로 결정한다. 개설 강좌 정렬은 편집 중인 화면 행을 이동하며 저장 전 입력값과 행의 식별자를 유지한다.

오류는 `{code, message, issues, currentRevision?}`이고 400/404/409/413/422/503 의미는 OpenAPI response에 따른다. 이름 입력 DTO와 ID 기반 조회 응답은 별도 schema다.

## C-07 로컬 운영 경계

백엔드는 loopback에만 바인딩하고 정적 UI와 같은 출처로 제공한다. `POST /session`은 허용 Host·Origin에서만 256-bit 이상 난수 토큰을 발급한다. 토큰은 서버 재시작 또는 최대 12시간 후 만료하고 URL·로그에 넣지 않는다. 모든 상태 변경은 `X-Glorycourse-Session`을 검증한다.

자료 보관·재등록은 수강신청·수강이력 현황 Excel을 사용한다. 수동 백업·복원 화면과 Recovery API는 제공하지 않는다. 일반 자료 변경, Excel 반영, 배정 확정은 자동 백업하지 않으며 DB 마이그레이션은 적용 전 `update-backups` 안전 사본을 유지한다.

수강이력 Excel 양식 버전 `2`는 학생별 관리자 메모와 별도 개설강좌 시트의 정원을 보존한다. 정원 미정은 `미정`으로 구분하며 기존 정원 충돌은 유지 또는 파일 값 적용을 명시적으로 선택한다. 같은 이력은 기존 메모를 유지한다. 신청 현황은 조회된 신청의 학기 순서와 전체 개설강좌 정원을 보존하며 미정은 공란이다. 배정초안·시스템 기록은 Excel에 포함되지 않는다.

## C-08 실데이터

대상 OS와 배포 검증 절차는 [배포 문서](releasing.md)에 기록한다. 자동 테스트의 합성 fixture 결과와 고객 PC·익명화 실데이터 검증을 구별한다. 실제 자료 검증에는 회원·신청·강좌 규모, 환경과 결과를 기록하되 공개 저장소에 원본 명단·백업을 올리지 않는다.

## C-09 런타임과 도구

최소 런타임은 Node.js `>=22.14.0`이며, 개발용 `node` 의존성·`.nvmrc`·배포 설정·CI는 `22.23.3`을 사용한다. `npm ci` 후 npm scripts는 프로젝트 Node를 우선 사용하며, `--ignore-scripts` 설치는 지원 버전의 시스템 Node를 먼저 준비해야 한다. 루트 `package-lock.json`으로 실제 설치 버전을 고정한다. 계약 검증은 Node test runner, Ajv 8, YAML 2, Redocly CLI 2를 사용한다. 저장과 HTTP는 Node 내장 모듈, xlsx는 `@excel.js/exceljs`, 프런트는 HTML/CSS/JavaScript를 사용한다. 하위 디렉터리에 별도 Git 저장소나 비공개 dependency를 두지 않는다.

## 수동 일괄 등록

신청과 이력을 요청당 1~100건 등록한다. 신청은 `POST /applications/batch`에서 이름 Resolve와 희망 강좌를 포함해 전부 반영하거나 전부 거절한다. 이력은 `POST /enrollments/batch/preview`로 행 순서대로 누적 검증한 후 `POST /enrollments/batch`로 전부 반영한다. 준비 토큰은 전체 입력·revision·epoch·경고 digest·만료를 묶고 단건 작업과 혼용하지 않는다. 동일 학기·회원 중복은 오류, 정원·재수강 등 기존 경고는 묶음 전체로 확인하며 관리자 메모는 선택 입력이다. 오류 메시지와 detail에 1부터 시작하는 행 번호를 포함한다.

화면의 `입력 경고 무시`는 안내·경고 표시와 확인 창을 생략하는 설정이다. 서버의 오류 검사·충돌 선택·warningDigest 검증을 끄지 않는다. 메모는 비워도 되며 최대 2,000자다. Excel의 학생별 메모가 공통 경고 확인 메모보다 우선하고, 같은 이력이 있으면 기존 메모를 유지한다. 이 설정은 배정 확정 검토에 적용되지 않는다.

## 수동 초안

`MANUAL` 초안은 배정 정책을 적용하지 않고 신청자를 미배정으로 시작한다. 정책 필드는 기존 저장 형식과 fingerprint 구성을 유지하기 위해 보관한다. `POST /allocation-drafts/{id}/items`는 수동 초안에서만 이름 기준 회원 Resolve와 강좌 배정을 하나의 트랜잭션으로 수행하며 신청 자료를 만들지 않는다. 중복 초안 회원·같은 학기 기존 이력·타 학기 강좌를 거절하고 초안 revision을 검증한다. 추가한 행도 기존 최종 결정 수정·정원 현황·확정 검증을 사용한다.

## C-10 engineVersion

첫 배정 엔진 버전은 `1.0.0`으로 시작한다. replay는 저장된 inputSnapshot·policyVersion·policySettings·seed와 정확히 같은 engineVersion 구현이 있을 때만 재현으로 표시한다. 지원하지 않는 버전은 명시적으로 재현 불가를 반환하며 live 자료로 대신 계산하지 않는다.

## JSON Schema 밖의 불변조건

복합 유일성, 교차 엔티티 참조, 동일 학기 관계, auto/snapshot 불변, receipt 선조회는 후보 전체를 가진 서비스 계층에서 검증한다. JSON Schema 통과만으로 업무 불변조건을 모두 충족했다고 판단하지 않는다.

## C-11 홈과 학기 업무 완료

`frontend/dashboard-view.js`가 현재 학기 선택과 다음 할 일을 결정한다. 학기는 `order` 내림차순, `null`은 마지막이며 가장 큰 유효 순서의 학기가 현재 학기다. 순서가 있는 학기가 없으면 학기 추가부터 안내한다. 이름이나 시스템 날짜로 현재 학기를 추정하지 않는다.

다음 할 일은 학기 없음 → 개설 강좌 없음 → 정원 미입력 → 신청 없음 → 진행 중 초안 없음 및 확정 기록 없음 → 검토 초안의 원본 변경 → 초안 검토/확정 → 현황 다운로드 → 완료 순서로 판단한다. 먼저 해당하는 조건이 우선한다. 확정 기록이 있어도 앞 단계 조건이 충족되지 않으면 완료 표시가 나오지 않는다.

배정 확정은 선택된 수강이력과 재시도용 영수증을 같은 트랜잭션에 저장하고 확정 초안과 항목을 삭제한다. 수강이력 조회는 영수증이나 초안에 의존하지 않는다. `GET /semesters/{id}/enrollment-report`는 확정·현황 다운로드 상태를 조회하고, `POST`는 해당 학기의 전체 수강이력을 XLSX로 생성하며 다음 규칙으로 기록한다.

- 확정 기록이 없는 학기의 다운로드 요청은 422, 저장소 리비전 또는 세대 충돌은 409다.
- 서버가 생성 시작 시점의 `storeEpoch`·`storeRevision`을 보관하고 저장 시점까지 동일한지 검증한다. 생성 중 내부 저장소 교체 등으로 epoch가 바뀌면 revision이 같아도 기록을 거절한다.
- 확정 영수증에 `enrollmentReportDownloadedAt`과 반영 후 `enrollmentReportStoreRevision`을 저장한다. 현재 자료에서 이미 기록된 동일 요청은 추가 쓰기를 하지 않는다.
- 조회의 `enrollmentReportIsCurrent`는 저장된 리비전과 현재 `storeRevision`의 일치 여부다. 현재는 학기별 변경 범위가 아니라 전체 저장소 리비전이므로 다른 학기 자료 변경도 재다운로드 안내를 만들 수 있다.
- 기록 시점은 파일 생성 후 응답 반환 전이다. 브라우저에서 실제 저장을 마쳤거나 파일을 읽었는지까지 확인하는 기능은 아니다.

화면은 현재 학기의 확정 기록에 이 API를 연결한다. 일반 `GET /enrollments/export`는 검색 조건에 맞는 파일만 반환하며 완료 기록을 남기지 않는다. 필수 진행 단계는 학기·강좌 설정, 수강신청, 배정초안, 수강이력의 네 단계다. 과거 이력만 직접 입력하는 사용 방식은 가능하지만 별도의 학기 업무 완료 기록을 만들지는 않는다.

## C-12 학기·강좌와 이력의 변경 범위

- 학기 생성 시 순서를 생략하면 기존 유효 최대 순서에 1을 더한다. 순서는 양의 정수이며 중복할 수 없다. 순서가 없는 학기의 문맥 저장과 자동 초안 생성도 필요한 순서를 부여한다.
- 이름 비교는 앞뒤 공백 제거와 Unicode NFC 정규화를 사용한다. 같은 이름은 같은 회원·강좌로 해석하며 별도의 동명이인 식별자는 입력받지 않는다.
- 학기명은 해당 학기를 참조하는 신청·이력에, 강좌명은 공통 강좌를 참조하는 모든 학기에 반영된다.
- 학기별 개설 강좌 삭제는 그 개설 강좌의 수강이력이 있으면 거절한다. 신청만 있으면 명시적 확인 후 관련 희망을 제거하고, 희망이 남지 않은 신청도 삭제한다.
- 신청·진행 중 배정초안은 이력과 독립적으로 삭제할 수 있다. 확정 시 초안은 삭제되고 이력과 최소 확정 기록만 남는다.
- 여러 강좌 입력·이전 학기 복사는 화면에 강좌명·정원 후보를 추가하며 문맥 저장으로 확정한다. 신청·이력을 복사하지 않는다.

## C-13 Excel 양식과 현황

신청 양식 `GET /applications/template`은 `semesterId`를 요구한다. 선택 학기의 이름·순서를 `학기`, 해당 학기의 강좌명·정원을 `개설강좌` 시트에 포함한다. 강좌가 없으면 빈 시트이며 이전 학기 자료로 자동 대체하지 않는다. 신청은 학기·회원당 한 행이며 기본 양식에는 `1순위 강좌`부터 `3순위 강좌`까지 제공한다. 사용자가 오른쪽에 `4순위 강좌`·`5순위 강좌` 열을 추가할 수 있으며 빈 순위는 건너뛴다. 파서는 순위 열을 반복 처리하고 `MAX_CHOICES_PER_APPLICATION = 5` 상수로 최대 개수와 순위를 제약한다. 2~5순위는 선택 사항이며 희망 강좌는 최소 1개다. 직접 입력·API·자동 배정도 선택지와 순위를 최대 5개로 제한한다. 신청·이력 양식 버전은 모두 `2` (`TEMPLATE_VERSIONS`)이며 이전 버전 양식은 지원하지 않는다. 신청 현황과 보관 원본을 내보낼 때는 필요한 순위 열을 포함한다.

이력 양식·일반 현황·현재 학기 현황은 `수강이력` 시트의 `학기명·회원명·강좌명·관리자 메모`, `개설강좌` 시트의 `학기명·강좌명·정원`을 제공한다. 현황에는 내려받는 이력에 해당하는 개설강좌만 중복 없이 포함하며 기존 정원을 보존한다. 정원 미정은 `미정`, 정원 0은 숫자 0으로 기록한다. 적어 둔 강좌 행의 정원 공란은 오류이며 기존 정원과 다르면 명시적으로 유지 또는 파일 값 적용을 선택한다.

화면 다운로드 이름은 `frontend/download-name.js`에서 한국어 종류와 브라우저 로컬 시각의 `YYMMDDHHMMSS`로 생성한다. 예를 들어 `수강신청_양식_260925143015.xlsx`, `수강이력_현황_260925143015.xlsx`다. 신청·이력 일반 현황은 같은 검색 조건의 전체 결과이며 목록 페이지 크기에 제한되지 않는다.

신청 현황 `GET /applications/export`는 검색·정렬한 신청에서 학기 ID를 중복 제거하고 해당 학기별 이름·순서와 전체 개설강좌의 이름·정원을 시트에 기록한다. 다른 학기는 포함하지 않으며 검색에 해당하지 않는 강좌도 대상 학기의 개설강좌라면 포함한다. 미정 순서·정원은 공란, 정원 0은 숫자 0으로 기록한다. 결과가 없으면 열 제목만 제공한다. 조회는 저장소를 변경하지 않는다.
