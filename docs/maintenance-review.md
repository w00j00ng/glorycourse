## 목표와 작업 원칙

교회 관리자가 자료를 입력·검토·확정하고 프로그램을 종료하는 과정에서 자료가 손실되거나 잘못 표시되는 결함을 찾고 수정한다. 재현되는 문제와 그 원인을 줄이는 리팩터링에 집중한다. 새 기능, 프레임워크 교체, 전면적인 파일 재배치는 이번 범위에 포함하지 않는다.

작업 시작 시 주간 한도 잔여량은 40%이며 예정 리셋은 2026-10-01 23:33(한국 시간)이다. 작업 단위마다 실제 한도를 확인하고 잔여량이 100%로 리셋되면 중단한다. 리셋 크레딧을 사용하지 않는다.

## 진행 순서와 검증

1. **기준 확인:** 전체 검증과 커버리지를 실행하고 기존 실패와 새 결함을 구분한다.
2. **저장·복구·HTTP:** 쓰기 직렬화, 실패 후 재시도, 백업·복원, 업로드 제한, 종료를 검토한다. 실제 요청이나 저장 결과를 검사하는 회귀 테스트로 보완한다.
3. **업무 처리:** Excel 검토·반영, 학기·강좌 변경, 수강이력, 배정 및 확정의 입력 검증과 오래된 검토 결과 처리 여부를 확인한다.
4. **화면 일관성:** 검색·페이지 이동·학기 선택·팝업의 비동기 요청과 오류 처리를 확인한다. 사용자 조작 순서에 따른 화면 결과를 검증한다.
5. **배포·문서:** 실행·종료·패키징 경로와 사용자 안내를 확인한다. 필요한 패키지 검증을 실행한다.
6. **마무리:** 보완한 내용을 다시 검토하고 전체 `npm run verify`를 통과시킨다. 한글 conventional commit으로 작업 단위를 나누어 커밋·푸시한다. `main` 병합과 릴리스는 수행하지 않는다.

사용자의 후속 지시에 따라 일반 저장의 전체 테이블 재삽입 문제를 최우선으로 전환했다. 변경 행 저장, 관계·순서 교환, 롤백과 강제 종료 복구를 먼저 검증한다.

## 보완 결과

### HTTP 요청 검증

- 배정초안 API에 `null`을 전송하면 500 서버 오류가 발생함을 재현했다. 공통 JSON 읽기 함수에서 객체가 아닌 입력을 400으로 거부한다.
- 배정 설정이 누락되거나 `null`이면 500이 발생했다. 기존 설정 검증에서 누락을 처리하여 422 업무 입력 오류로 반환한다.
- 실제 HTTP 요청으로 여러 API의 잘못된 입력과 자료 불변을 검증했다. 길이를 미리 알 수 없는 업로드의 용량 초과 응답도 확인했으며 서버 구현 변경은 필요하지 않았다.
- 검증: HTTP·초안 통합 테스트 19개, `npm run typecheck` 통과.
- 한도 재확인: 주간 잔여 37%, 리셋 시각 변경 없음.

### 목록 및 학기 편집의 응답 순서

- 빠르게 검색·페이지·표시 건수를 바꿀 때 이전 요청의 응답이 마지막 선택을 덮어썼다. 목록 데이터와 페이지 정보는 마지막 요청만 반영한다.
- 수강이력의 현황 다운로드 안내도 이전 요청의 결과로 되돌아가지 않도록 함께 보호한다.
- 학기 A→B→A 선택과 학기 목록이 비는 경우를 포함해, 늦은 응답이 다른 학기의 편집 화면을 열지 않도록 한다. 조회 중에는 이전 편집 양식을 숨긴다.
- 이전 학기 강좌 복사 원본을 A→B→A로 바꾸거나 복사 창을 다시 열 때도 과거 조회 응답이 현재 목록을 덮지 않도록 한다.
- 삭제 후 마지막 페이지 보정은 유지하고, 오래된 요청에 따른 불필요한 재조회는 차단한다.
- 검증: 수정 전 실패 재현, 화면 관련 테스트 13개·JavaScript 구문·diff 검사 통과.

### 백업의 실제 복원 가능 여부

- 마이그레이션 기록과 메타 정보가 남아 있는 손상 백업을 정상으로 표시하고 재사용하는 문제를 재현했다.
- 현재 버전 백업은 실제 테이블과 자료를 읽고 기존 스키마 검증을 통과해야 정상으로 표시한다. 손상 백업을 보존하면서 새 정상 백업을 생성한다.
- 누락된 자식 테이블·잘못된 날짜 두 사례와 정상 백업의 중복 방지, 현재 자료 불변을 검증했다.
- 구버전 백업은 기존대로 복원 미리보기에서 임시 사본을 갱신하고 전체 검증한다. 현재 버전 백업 목록 조회에는 자료 검증 비용이 추가된다.
- 검증: 저장·복원·SQLite·마이그레이션 테스트 35개 및 typecheck 통과.

### 저장·복원 실패 처리 정리

- 저장과 복원의 중복된 영속화·실패 후 재조회 코드를 `Store` 내부의 한 메서드로 통합했다.
- 실패 시 이전 자료가 유지된 경우 재시도, 이미 반영된 경우 성공 복구, 결과를 판단할 수 없는 경우 추가 쓰기 차단이라는 기존 동작을 유지한다.
- 두 작업 × 네 가지 저장 결과의 회귀 테스트를 리팩터링 전후 실행했다. SQLite 재개방·복원·마이그레이션 포함 35개 테스트와 typecheck를 통과했다.

### 200건을 넘는 기준 자료 조회

- 회원·강좌·학기 목록에서 첫 200건만 읽어 이후 자료가 선택 항목에서 누락됐다. 기존 API의 모든 페이지를 읽는 공통 함수를 사용하도록 수정했다.
- 0·200·201·401건, 최신 학기 기본 선택, 기존 학기·강좌 필터 유지와 초안의 회원 선택 항목을 검증했다.
- 관련 화면 테스트 20개를 통과했다. API는 기존의 페이지 단위 조회를 유지하므로 다른 창에서 조회 도중 자료를 변경하면 새로고침이 필요할 수 있다.

### 일반 저장의 전체 테이블 재삽입 제거

- 지적은 타당했다. `Store.write()`는 작은 수정도 `writeRelationalStore()`의 전체 DELETE·INSERT 경로로 보냈다. 실제 파일에 감사 트리거를 설치해 회원 이름 한 건 변경이 Excel 원본·배정 스냅샷까지 재작성함을 재현했다.
- 일반 저장은 이전 상태를 어댑터에 전달하고, 변경된 행만 INSERT·UPDATE·DELETE한다. 큰 자식 컬렉션은 부모 메타 정보만 바뀌어도 재작성하지 않는다. 초기 생성·복원에는 전체 교체 경로를 유지한다. DB 스키마·마이그레이션 변경은 없다.
- SQL과 값 매핑은 기존 관계형 쿼리 계층에서 재사용한다. 트랜잭션 안에서 epoch·revision을 확인하고, 순서·고유 값 교환과 삭제를 처리한다. 부모가 삭제된 뒤 다른 부모로 이동한 자식의 원본 참조도 보존한다.
- 검토 중 중복 ID가 필터에서 누락될 가능성과 기존 마이그레이션으로 position에 공백이 남는 사례를 발견해 추가로 보완했다.
- 실제 파일 회귀 테스트 9개: 정확한 변경 건수, 초안 자동 근거와 가져오기 원본 보존, 이름·관계 교환, 순서 공백·중간 삽입, 중복 ID 거부, 오래된 상태 거부, 롤백·재시도와 저장 응답 유실 복구를 검사한다. `npm run verify`에 포함한다.
- 강제 종료 검증은 기존 회원을 삭제하고 20만 명을 추가하는 작업을 전체·부분 저장 경로 각각에서 중단한다. 재시작 결과가 완전한 이전/새 상태 중 하나인지 검사한다.

`npm run test:storage-scale`은 각 규모마다 동일한 합성 자료를 별도 DB에 넣고 회원 한 건 수정을 3회 측정한다. 회원·신청·희망 강좌·과거 수강이력·Excel 원본·초안 스냅샷·초안 항목을 함께 넣었다. 다음은 로컬 Windows 측정 예이며, 시간은 기기와 부하에 따라 달라진다. 비교 기준은 보존된 전체 교체 저장 경로다.

| 회원 수 | 전체 교체 중앙값 | 부분 저장 중앙값 | SQLite 변경 행 수 |
| ---: | ---: | ---: | ---: |
| 1,000 | 70.1ms | 6.0ms | 30,094 → 2 |
| 10,000 | 836.8ms | 19.0ms | 300,094 → 2 |

`Store.write()`는 변경 경로만 복사하고 변경 행과 메타데이터만 기존 JSON Schema로 검증한다. 변경하지 않은 컬렉션은 SQL 비교를 건너뛴다. DB 열기·복원은 전체 검증을 유지한다. **남은 비용:** 수정된 컬렉션의 배열 복사·행 탐색은 여전히 해당 컬렉션 크기에 비례한다. 외부 변경을 막는 `Store.read()`의 전체 복제도 조회 경로에 남아 있다. 위 측정은 직접 쓰기 명령이며 모든 HTTP 업무의 응답 시간을 뜻하지 않는다.

### 대량 초안 화면과 재시도

- 초안 상세를 50명씩 표시하고 필터·정렬은 전체 결과에 적용한다. 강좌 선택지는 해당 행의 선택창에 초점이 갈 때, 상세 배정 근거는 펼칠 때 생성한다.
- 합성 회원 1만 명·강좌 1천 개로 실제 브라우저에서 확인했다. 첫 페이지의 결과 행은 50개, 결과 선택지는 100개였고 선택창 하나를 열었을 때만 그 창에 1,001개가 생성됐다. 다음 페이지, 검색 후 첫 페이지, 결정 저장·색상 표시·자동 복원, 상세 근거와 도움말 연결을 확인했다.
- 확정·복원 확인 메모가 잘못되어 422로 거부된 뒤 수정하면 새 입력으로 재시도한다. 확인 메모 오류는 수강이력·확정·가져오기·복원 모두 수정 방법을 한국어로 안내한다. 서버 응답이 불확실한 통신 오류에서는 기존 요청과 멱등 키를 그대로 유지한다. 늦은 실패 응답이 새 입력을 지우는 경우도 검사했다.
- 기존 중복 도메인 타입과 강제 형변환 18곳을 공통 저장 타입으로 대체했다. 실행 로직은 변경하지 않았다.

### 후속 화면 검증과 책임 분리

- Playwright의 실제 Chromium 테스트로 학기·강좌 등록 → 신청 → 초안 검토·확정 → 수강이력 재조회, 잘못된 확정 메모 수정 후 재시도, 로고 이동, 새로고침 후 페이지 유지, 도움말을 검증한다. 신청 없이 과거 수강이력 2건을 한 번에 등록하고 경고를 확인한 뒤 학기·강좌가 함께 생성되는 흐름도 검사한다. 내려받은 신청 양식의 Excel 검토·반영과 수동 백업 중복 방지·복원 전 검토·자료 복원도 확인한다. 별도 합성 자료로 500명 초안의 50행 페이지 처리와 선택 행의 강좌 옵션 지연 생성을 검사한다. CI에서 `test:browser`를 독립 작업으로 실행한다.
- 대시보드의 조회·표시·업무 흐름 카드를 `frontend/dashboard-page.js`로 분리하고 기존 순수 판단 함수와 도움말 원본을 그대로 사용한다. 자료 관리의 백업·복원은 `frontend/backups-page.js`, 배정 확정의 미리보기·재시도는 `frontend/finalization-page.js`로 옮겼다. 두 모듈을 직접 호출해 거절·불확실한 응답 재시도를 검사하고, 다른 초안으로 이동한 뒤 도착한 늦은 확정 미리보기가 열리지 않게 했다. 수강신청의 목록 조회·수동 등록·수정·삭제·양식 다운로드를 `frontend/applications-page.js`로 분리해 직접 테스트했다. 학기·강좌 목록의 선택·순서 이동·상세 조회·추가·이름 수정·삭제와 이전 학기 강좌 조회를 `frontend/catalog-page.js`로 옮겨 늦은 응답을 직접 테스트하고 관리자 흐름을 브라우저에서 확인했다. 이 화면 모듈들과 배정초안 표시·파일명·안내 문구 모듈은 `checkJs`의 엄격 검사에 포함한다. 나머지 `app.js`의 화면 책임은 여전히 크고 타입 검사 대상도 아니다. 후속 분할 순서는 [저장 경로와 화면 분할 계획](refactoring-plan.md)에 기록했다.
- 브라우저 테스트는 주요 업무 흐름과 대량 초안 화면을 보호하지만 전체 프런트엔드를 실행하지 않는다. `test:coverage`의 프런트엔드 줄 수치는 별도 Node 실행 기준이므로 브라우저 검증 범위를 대신하지 않는다.

### 최종 검증과 한계

- `npm run test:coverage`는 저장 변경과 첫 화면 분리 후 통과했다. 이후 화면 모듈의 직접 테스트를 추가한 `npm run verify`는 기능·계약 194개, 강제 종료 복구 3개, 실행기 5개 모두 통과했다. 실제 브라우저 테스트 7개도 통과했다. 앞서 측정한 Backend 줄 커버리지 94.15%, Frontend 27.94%는 Node 테스트 기준이며 새 화면 테스트를 포함한 재측정값은 아니다. 브라우저에서 실행한 줄은 합산하지 않는다. README에 수치를 기록하거나 coverage 커밋을 생성하지 않는다.
- `npm run test:storage-scale` 2개 통과. 저장 코드의 마지막 수정 뒤 재측정한 값을 위 표에 기록했다. 배정 부하 2개와 대용량 Excel 검증 1개도 통과했다.
- 학기 화면 모듈을 포함해 `npm run package`, `npm run test:package`를 다시 실행해 통과했다. Windows 압축 파일 무결성, 동봉 런타임, 중복 실행, 저장·Excel·백업/복원, 종료 API·재시작·종료 파일을 검증했다. 로컬 검증용 빌드이며 릴리스로 공개하지 않았다.
- macOS·Linux 실제 GUI는 이 환경에서 확인하지 않았다. 실제 브라우저 검증에는 별도의 임시 합성 자료를 사용했고, 검증용 서버·탭·스크립트는 정리했다.
- 마지막 한도 확인은 주간 잔여 20%이며 리셋 시각은 변경되지 않았다. 리셋 크레딧을 사용하지 않았다.
